# LCD 1602A D4 接线错位导致 C/B/A 字符相同

**时间**：2026-09-03 03:xx

## 现象

v16-diagnostic 固件显示 "FEDCBA9876543210"（ONLINE 阶段），摄像头拍摄后分析：
- 位置 3-5 (C,B,A)：三个完全相同的实心方块
- 位置 0-2 (F,E,D)：F 和 E 显示为相同字符（'F'），D 正常显示

## 根因

D4 导线（GPIO5）在重新插入时插到了 LCD 引脚 12（D5）位置，导致：
- GPIO5 和 GPIO6 都驱动 LCD D5 引脚
- LCD D4 引脚（pin11）悬空，始终读为 0

数学验证（write_nibble 中 D5 = OR(bit0, bit1)，D4 = 0）：
- A（low=0001）：D5=OR(1,0)=1，D4=0 → low nibble=0010 → char 0x42='B'
- B（low=0010）：D5=OR(0,1)=1，D4=0 → low nibble=0010 → char 0x42='B'
- C（low=0011）：D5=OR(1,1)=1，D4=0 → low nibble=0010 → char 0x42='B'
- 三者全部显示为 'B'（相同）✓

## 教训

- 在深夜/遥控状态下重新插线容易插错位置
- 4-bit LCD 的 D4-D7 引脚序号（11-14）很容易看错一个
- 下次插线后应立即用摄像头确认字符显示，或用万用表确认导通

## 修复方法

硬件修复：将 GPIO5 的导线从 LCD pin12（D5）拔出，插回 LCD pin11（D4）

此问题**无法通过固件修复**——GPIO 无法向悬空引脚发送数据。

## 当前状态

v16-diagnostic OTA 成功，mark_valid 已修复。主线任务（网页远程播报）的 play_audio 已验证正常。
stop_audio 待白天（22:00 前）验证。
LCD 显示待端侧修复接线后恢复正常。

## 第二次接线故障：D6/D7 互换（2026-09-03 08:3x）

**时间**：2026-09-03 08:30–08:40

### 现象

用户修复了 D4 错位后，重新拍照+重启设备。BOOTING 画面（"0123456789ABCDEF"）分析：
- 位置 0-3（0,1,2,3）：显示可辨字符（正常）
- 位置 4-9（4,5,6,7,8,9）：显示乱序字符（4→8, 5→9 等）
- **位置 10-15（A,B,C,D,E,F）：全部显示为实心方块（CGRAM 乱码）**

### 根因分析

`A`-`F` 高半字节固定为 `0x4 = 0100`，其中 **bit2=1**。
`0`-`3` 高半字节固定为 `0x3 = 0011`，其中 **bit2=0, bit3=0**。

若 D6（GPIO7）和 D7（GPIO8）物理位置互换（GPIO7→LCD pin14, GPIO8→LCD pin13）：

- bit2 信号走到 LCD D7（而不是 D6）→ LCD 高半字节 bit3 被设为 1 → 高半字节变成 `0x8`
- `A`-`F` 全部进入 HD44780 CGRAM 区（0x80-0x8F = 自定义字符 = 未初始化乱码）→ 实心块 ✓

验证：位置 9（'9'）预测显示 '5'，摄像头看到 'S'（'5' 在 5x8 字体就是 S 形）✓

`0`-`3` 低半字节 bit2=bit3=0，D6/D7 交换对它们无影响 → 正常显示 ✓

### 修复方法

**固件修复**（比硬件重新插线更简单）：
在 `audio_board_config.h` 中交换 D6/D7 定义：
```c
#define LCD_D6  GPIO_NUM_8   // 原为 GPIO_NUM_7
#define LCD_D7  GPIO_NUM_7   // 原为 GPIO_NUM_8
```

**已修改固件** → v17-lcd，OTA 上线后验证。

**教训**：GPIO7→pin13(D6) 和 GPIO8→pin14(D7) 物理位置相邻，重新接线时容易插反。
固件版本号应在每次接线后立刻验证显示内容，避免多轮反复。

## 第三次故障：v17/v18 固件补偿 + 用户再次修复接线（2026-09-03 09:0x）

**时间**：2026-09-03 09:00–09:30

### 过程

- v17-lcd（仅 D6/D7 补偿）OTA 后摄像头图像依然乱码，分析判断 D4/D5 也被互换
- v18-lcd（D4↔D5 + D6↔D7 双向补偿）OTA 上线，设备报告 fw=v18-lcd
- 用户此时说明："修复接线了，接线一致都是正确的"（接线已恢复为原始正确接线）

### 根因

v18-lcd 包含固件补偿（GPIO5↔GPIO6, GPIO7↔GPIO8），此补偿假设物理接线仍是错的。
用户修复接线后，正确接线 + 补偿固件 = 二次互换 = 再次乱码。

### 修复方法

还原固件到原始 GPIO 定义（无补偿）→ v19-lcd：
```c
#define LCD_D4  GPIO_NUM_5   // 原始
#define LCD_D5  GPIO_NUM_6
#define LCD_D6  GPIO_NUM_7
#define LCD_D7  GPIO_NUM_8
```

v19-lcd OTA 成功（2026-09-03 09:26，fw 已确认 v19-lcd），设备在线。

### 当前状态（待确认）

摄像头因物理位置改变导致拍摄角度变差，无法清晰读取 LCD 字符。
从图像可见字符形态为细线笔画（非实心 CGRAM 块），与接线正确时预期一致。
**需人工直视 LCD 确认是否正确显示 "FEDCBA9876543210" / IP 地址。**

### 教训

固件补偿方法只有在接线不变的情况下有效。接线修复后必须同步还原固件到原始 GPIO 定义。
每次接线改动后记录当前固件版本，避免"接线修了，固件补偿还在"的混乱状态。

## v20-boot 开机播报 bug：/boot_announce URL 路径不匹配（2026-09-04 06:5x）

**现象**：刷入 v20-boot 后手动重启 ESP32，设备无任何播报。

**根因**：端侧 `hub.boot_announce()` 调用 `POST /boot_announce`（device_id 在 body，与 `/register`、`/heartbeat` 保持一致），但云侧路由写成了 `/api/device/{device_id}/boot_announce`（device_id 在 URL path），路径不匹配 → 404 静默失败。

**修复**：server.py 新增 `@app.post("/api/boot_announce")` 扁平路由，读 body 里的 device_id，复用同一内部函数 `_boot_announce_for()`。原有 `/api/device/{device_id}/boot_announce` 保留（供平台页面手动触发）。

**验证**：重启后 `c-e3e1ea` status=done，音量=40%，transport=mqtt，全链路 9 秒内完成 ✅
