# 运行版本与假阳性验证

“命令成功”“服务健康”和“新版本正在运行”是三个不同命题。发布或远程配置变更必须建立从输入到运行结果的证据链，不能只检查最终业务表象。

## 四层来源

| 层级 | 要记录的证据 | 只能证明什么 |
|---|---|---|
| Git | commit SHA、分支、工作树状态 | 预期源代码版本 |
| CI/制品 | run ID、制品名与 SHA256、测试结果 | 某份输入被构建并通过指定检查 |
| 云端 | release 目录、镜像 ID/digest、容器启动时间、服务 revision | 云端实际运行的版本 |
| 边缘设备 | `RELEASE_INFO`、关键文件 SHA256、unit 状态、启动时间 | 指定设备实际安装并运行的版本 |

任何一层缺失时都只能报告到已证实的层级。例如云端健康而 Pi 部署步骤失败，只能说“云端发布成功，Pi 版本未知或未更新”，不能说“发布完成”。

## 最小验收记录

```text
git_commit=
ci_run_id=
artifact_sha256=
cloud_release=
cloud_image_id=
cloud_started_at=
edge_device=
edge_release=
edge_file_sha256=
edge_unit_state=
public_health=
real_device_check=
rollback_target=
```

接口最好直接返回不可伪造或不易漂移的 revision 字段。若只能检查某个新字段或 UI 文案，应明确它只是兼容性标记，不等同于完整 commit 身份。

## 服务改动的双重验证

配置由某个 service 或脚本应用时，同时验证：

1. 执行者：本次 boot/run 的退出码、日志和时间戳；
2. 结果：真实网络、API、设备动作或 SSH 端到端行为；
3. 排他性：确认结果不是旧缓存、旧容器、其他 profile 或备用进程产生的；
4. 持久性：重启后重新验证，而不是沿用变更前会话。

## 发布流水线的未闭环状态

流水线若在更新生产后才运行集成测试，或边缘部署使用 `continue-on-error`，其成功状态只代表允许部分成功，不代表云边版本一致。修复这类策略前必须先定义产品选择：边缘离线时是阻止云端发布、排队补发，还是允许明确标注的部分发布。没有这个决策时，不应静默把 warning 当作完整成功。
